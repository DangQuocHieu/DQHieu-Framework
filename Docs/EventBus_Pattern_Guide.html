Event Bus Pattern (EventBus) trong Unity

Giải phẫu toàn diện mô hình static EventBus trong C# & Unity: cơ chế Type Specialization O(1), tối ưu Zero-GC với readonly struct, xử lý bẫy Domain Reload, ưu nhược điểm và bộ code chuẩn Production.

💡
Góc Nhìn Senior: Tại sao EventBus<T> vừa là "cứu tinh" vừa là "con dao hai lưỡi"?
Mô hình public static class EventBus<T> (chỉ với một Action<T> OnEvent và 3 hàm Subscribe, Unsubscribe, Raise) là một trong những cách cài đặt Event Bus thanh lịch và nhanh nhất trong C#/Unity. Nó cắt đứt hoàn toàn dây chằng phụ thuộc giữa các hệ thống (Combat, UI, Audio, Analytics). Tuy nhiên, chính sự tiện lợi của static lại khiến nhiều lập trình viên dính bẫy Memory Leak (GC Root giữ xác object), Zombie Listener khi tắt Domain Reload, và Spaghetti Flow (khó trace luồng chạy khi lạm dụng). Tài liệu này sẽ bóc tách từ cơ chế CLR/IL2CPP bên dưới đến chuẩn cài đặt Production-ready.
PHẦN 1

Bản Chất Kỹ Thuật & Cơ Chế Nền Tảng

Để làm chủ EventBus<T>, trước tiên cần phân biệt nó với Observer truyền thống và hiểu cách C# Runtime (CLR / Mono / IL2CPP) biến một generic static class đơn giản thành kênh truyền tin tốc độ O(1).

1.1. Định nghĩa: Event Bus (Pub/Sub) vs Observer & C# event

Event Bus Pattern là một biến thể của kiến trúc Publish–Subscribe (Pub/Sub), sử dụng một kênh trung gian (Message Broker) để chuyển thông điệp theo kiểu dữ liệu. Khác với C# event trực tiếp (Observer), cả bên phát (Publisher) lẫn bên nhận (Subscriber) đều không cần biết sự tồn tại của nhau — chúng chỉ cần biết tới EventBus<T> và struct sự kiện T.

Tiêu chí Observer / C# event trực tiếp Event Bus (EventBus<T>)
Mức độ Coupling 1 chiều (Direct Coupling): Subscriber phải giữ tham chiếu trực tiếp tới instance của Publisher (player.OnDied += ...). Decoupled hoàn toàn (Zero Reference): Publisher và Subscriber độc lập tuyệt đối, dễ tách Assembly Definition (.asmdef).
Phạm vi giao tiếp 1–1 hoặc 1–N gắn chặt với vòng đời của một instance cụ thể. N–N toàn cục (Global Broadcast theo loại sự kiện T).
Quản lý vòng đời Khi Publisher bị hủy và GC thu hồi, danh sách delegate bên trong nó tự biến mất theo. Kênh static sống suốt vòng đời AppDomain — Subscriber bắt buộc phải tự Unsubscribe.
🔗 Kiến Trúc Tight Coupling vs EventBus<T> (Zero Reference)

1.2. Cơ chế Generic Static Class EventBus<T> trong CLR & IL2CPP

Điểm thiên tài của mô hình public static class EventBus<T> nằm ở cơ chế Type Specialization (Generic Static Fields) của C#:

⚡
Truy cập O(1) — Zero Lookup Overhead
Mỗi kiểu đóng (closed constructed type) như EventBus<PlayerDiedEvent> hay EventBus<ScoreChangedEvent> được runtime cấp phát một vùng nhớ static hoàn toàn độc lập. Khác với EventManager dùng Dictionary<Type, Delegate> phải băm typeof(T) và dò bucket mỗi lần Raise, EventBus<T>.Raise() nhảy thẳng tới địa chỉ tĩnh của kiểu đó.
⚙️
Bên dưới CLR (Mono) & IL2CPP (AOT)
Trên CLR/Mono, JIT tạo MethodTable riêng chứa static field cho từng T. Trên IL2CPP, trình biên dịch AOT sinh struct _StaticFields riêng cho mỗi T. Đặc biệt với struct event, IL2CPP sinh mã chuyên biệt hoàn toàn (không qua Generic Sharing) giúp tốc độ ngang ngửa C++ thuần và không Boxing.

1.3. Cơ chế cấp phát bộ nhớ, Boxing & Static GC Root

Hiểu rõ đường đi của bộ nhớ sẽ giúp bạn tối ưu hệ thống Event Bus đạt chuẩn Zero-GC Allocation trong vòng lặp gameplay:

  • Struct Event vs Class Event & Bài toán Boxing: Nếu event payload là class, mỗi lần gọi Raise(new DamageEvent(...)) sẽ cấp phát trên Managed Heap, tạo rác GC liên tục. Ngược lại, dùng readonly struct (gọn nhẹ ≤ 16–32 bytes) kết hợp với Action<T> generic giúp truyền tham số qua Stack / thanh ghi CPU với 0 Boxing, 0 Heap Allocation.
  • Delegate Invocation List (MulticastDelegate): Bản thân Action<T> là kiểu tham chiếu bất biến (immutable). Mỗi lần gọi += hoặc -=, CLR cấp phát một MulticastDelegate mới và bỏ lại instance cũ cho GC. Do đó, tuyệt đối không Subscribe/Unsubscribe trong Update().
  • Bẫy Static GC Root: Biến static tồn tại suốt vòng đời AppDomain và đóng vai trò là GC Root. Mỗi listener trỏ tới instance method đều giữ Strong Reference (_target) tới MonoBehaviour đó. Nếu GameObject bị Destroy() mà quên Unsubscribe, phần Native C++ bị xóa nhưng object C# trên Managed Heap vẫn bị giữ sống vĩnh viễn → Memory Leak.

PHẦN 2

Đặc Thù Trong Unity Engine

Cài đặt EventBus<T> thuần C# rất dễ, nhưng đưa vào Unity phải đối mặt với vòng đời MonoBehaviour, Object Pooling, đa luồng và đặc biệt là tính năng Disable Domain Reload.

2.1. Vòng đời MonoBehaviour: OnEnable/OnDisable vs Awake/OnDestroy

  • OnEnable() / OnDisable() (Khuyến nghị mặc định): Phù hợp cho UI, VFX, Enemy, Object Pooling. Khi trả object về Pool (SetActive(false)), nó tự Unsubscribe và ngừng tốn CPU xử lý event; khi bật lại, nó tự Subscribe.
  • Awake() / OnDestroy(): Chỉ dùng cho các Manager/Controller cần nhận event ngay cả khi script đang tắt (enabled == false) hoặc GameObject đang ẩn.
  • Cảnh báo lệch pha & thứ tự khởi tạo: Tuyệt đối không ghép OnEnable + OnDestroy (bật/tắt nhiều lần sẽ đăng ký trùng lặp N lần!). Ngoài ra, không nên Raise gameplay event trong Awake() vì các listener ở GameObject khác có thể chưa chạy tới OnEnable().

2.2. Bẫy "Disable Domain Reload" & Zombie Listeners

Trong Unity Editor (Project Settings → Editor → Enter Play Mode Settings), khi bạn tắt Domain Reload để vào Play Mode nhanh hơn, Unity không reset các biến static giữa các lần Stop và Play lại.

⚠️
Hiện tượng Zombie Listeners & MissingReferenceException
Nếu không dọn dẹp EventBus<T>, các delegate đăng ký từ Play Session 1 vẫn nằm nguyên trong biến static s_OnEvent ở Session 2. Khi Session 2 gọi Raise(), bus sẽ gọi nhầm vào các MonoBehaviour đã chết của Session 1 và ném lỗi MissingReferenceException.
🔄 Vòng Đời Static EventBus Khi Tắt Domain Reload

2.3. Multi-threading, Execution Order & Re-entrancy khi đang Raise

  • Unity Main Thread: EventBus<T> không thread-safe và Unity API chỉ chạy trên Main Thread. Nếu dùng Task.Run, cần đẩy sự kiện vào ConcurrentQueue rồi Raise trong Update().
  • Execution Order không xác định: Thứ tự chạy của các Subscriber phụ thuộc vào thứ tự gọi Subscribe() lúc runtime (thường theo thứ tự Hierarchy). Tuyệt đối không viết logic giả định Subscriber A chạy trước B.
  • Sửa đổi listener ngay trong lúc Raise (Re-entrancy): Nhờ Action<T> (MulticastDelegate) là immutable, khi đang s_OnEvent?.Invoke(e), nó duyệt trên snapshot tại thời điểm bắt đầu gọi nên không văng InvalidOperationException nếu có ai đó Unsubscribe giữa chừng (khác với tự dùng List<Action<T>> + foreach).
PHẦN 3

Ưu Điểm & Nhược Điểm Toàn Diện

Đánh giá khách quan các lợi ích về mặt kiến trúc/hiệu năng đối chiếu với những rủi ro tiềm ẩn khi vận hành EventBus<T> trong dự án thực tế.

✅
Ưu Điểm Nổi Bật
  • Decoupling tối đa: Publisher và Subscriber không giữ reference của nhau, triệt tiêu Circular Dependency giữa các .asmdef.
  • Type-safe tại Compile-time: Loại bỏ hoàn toàn lỗi gõ sai chuỗi như string-based event ("OnPlayerDead"), tận dụng tối đa IntelliSense.
  • Hiệu năng O(1) & Zero-GC: Truy cập thẳng static field, không tốn hash lookup của Dictionary, không Boxing nếu payload là readonly struct.
  • Siêu gọn nhẹ: Chỉ ~20–50 dòng code cốt lõi, dễ hiểu, không cần kéo theo thư viện hay DI Container nặng nề.
❌
Nhược Điểm & Rủi Ro
  • Memory Leak qua Static GC Root: Quên Unsubscribe sẽ giữ xác object trên Managed Heap vĩnh viễn; tắt Domain Reload gây Zombie Listeners.
  • Implicit Control Flow (Khó Debug): Bấm "Find All References" vào Raise() không thấy ngay hàm nhận, khó trace khi chuỗi event nối tiếp nhau.
  • Khó Unit Test / Mock: Dùng static global state khiến các bài test dễ nhiễu nhau nếu quên Clear() ở [TearDown].
  • Không kiểm soát thứ tự & Nguy cơ Loop: Thứ tự gọi listener ngẫu nhiên; Event A bắn B rồi B bắn ngược A sẽ gây StackOverflowException.
PHẦN 4

Ma Trận Quyết Định & Phương Án Thay Thế

Không có pattern nào là "viên đạn bạc". Hãy dùng bảng ma trận và cây quyết định dưới đây để chọn đúng công cụ giao tiếp cho từng bài toán trong Unity.

4.1. Khi nào NÊN dùng vs KHÔNG NÊN dùng EventBus<T>

Tình huống sử dụng Khuyến nghị Lý do kỹ thuật
Cross-system Broadcast (1-to-Many): Combat → HUD, Audio, VFX, Achievement NÊN DÙNG ✅ Các hệ thống thuộc domain khác nhau, không nên giữ tham chiếu trực tiếp lẫn nhau.
Sự kiện toàn cục: PauseGame, CurrencyChanged, QuestUpdated NÊN DÙNG ✅ Giảm spaghetti reference giữa các Scene Managers và UI Panels.
Quan hệ Cha–Con trực tiếp (1–1 / cùng Prefab): PlayerController → Animator KHÔNG NÊN ❌ Dùng C# event hoặc gọi method trực tiếp để code tường minh, dễ trace.
Logic phụ thuộc thứ tự chặt chẽ: Tính Giáp → Trừ Máu → Kiểm tra Chết → Rớt Đồ KHÔNG NÊN ❌ EventBus không đảm bảo execution order; hãy dùng pipeline tuần tự.
Cần trả về giá trị (Request–Response): CalculateFinalDamage() KHÔNG NÊN ❌ EventBus là Fire-and-Forget 1 chiều. Dùng Interface hoặc Direct Call.
Cần Undo/Redo, Replay, Lockstep KHÔNG NÊN ❌ Dùng Command Pattern để đóng gói hành động thành object có thể lưu lịch sử.

4.2. So sánh EventBus<T> với các giải pháp thay thế

Giải pháp Coupling Hiệu năng (Runtime / GC) An toàn & Debug Độ phức tạp
C# event trực tiếp Trung bình (1 chiều) Rất cao (O(1), 0 boxing) Rất dễ trace, tự hủy theo instance Rất thấp
EventBus<T> (Generic Static) Thấp (Decoupled) Rất cao (O(1) static field, 0 boxing với struct) Khó trace (Implicit flow), cần xử lý Domain Reload Thấp
Dictionary<Type, Delegate> Thấp (Decoupled) Trung bình (tốn Hash lookup, dễ dính Boxing) Dễ Clear() tập trung, chậm hơn EventBus<T> Thấp
ScriptableObject Event Channel Thấp (Asset-based) Tốt (UnityEvent có overhead nhẹ) Trực quan trong Inspector, sinh nhiều file .asset Trung bình
UniRx / R3 / MessagePipe Rất thấp (Scoped DI) Tốt nhất (Zero-alloc, tối ưu cao) Có AddTo(this) tự hủy, hỗ trợ Async/Unit Test Cao

PHẦN 5

Thực Chiến Đối Chiếu: Anti-Pattern vs Best Practice

Từ mẫu EventBus<T> tối giản nhất đến phiên bản chuẩn Production, dưới đây là 4 cặp code đối chiếu các lỗi phổ biến nhất mà lập trình viên Unity hay mắc phải.

5.1. Cài đặt EventBus<T>: Bản thô sơ vs Chuẩn Production (An toàn Domain Reload)

❌ ANTI-PATTERN: Không constraint, hở public field & chết khi tắt Domain Reload 
using System;

// Lỗi 1: Không có constraint -> ai cũng có thể tạo EventBus<int>, EventBus<string> gây rác type.
// Lỗi 2: Expose public static Action trực tiếp -> bên ngoài có thể gán "= null" xóa sạch listener khác!
// Lỗi 3: Không tự Clear() khi Disable Domain Reload -> Zombie Listeners & MissingReferenceException.
public static class NaiveEventBus<T>
{
    public static Action<T> OnEvent;

    public static void Subscribe(Action<T> listener) => OnEvent += listener;
    public static void Unsubscribe(Action<T> listener) => OnEvent -= listener;
    public static void Raise(T eventData) => OnEvent?.Invoke(eventData);
}
✅ BEST PRACTICE: Ràng buộc struct + IGameEvent, Đóng gói & Tự Clear khi SubsystemRegistration 
using System;
using System.Collections.Generic;
using UnityEngine;
#if UNITY_EDITOR
using UnityEditor;
#endif

public interface IGameEvent { }

internal static class EventBusRegistry
{
    private static readonly List<Action> s_ClearActions = new();

    public static void Register(Action clearAction)
    {
        if (!s_ClearActions.Contains(clearAction))
            s_ClearActions.Add(clearAction);
    }

    // Chạy sớm nhất mỗi khi vào Play Mode, KỂ CẢ KHI Disable Domain Reload
    [RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.SubsystemRegistration)]
    public static void ClearAllBuses()
    {
        for (int i = 0; i < s_ClearActions.Count; i++)
            s_ClearActions[i]?.Invoke();
        // LƯU Ý: KHÔNG gọi s_ClearActions.Clear() ở đây vì static ctor của EventBus<T>
        // sẽ không chạy lại ở Play Session sau nếu Domain Reload bị tắt!
    }

#if UNITY_EDITOR
    [InitializeOnLoadMethod]
    private static void InitEditor()
    {
        EditorApplication.playModeStateChanged -= OnPlayModeStateChanged;
        EditorApplication.playModeStateChanged += OnPlayModeStateChanged;
    }

    private static void OnPlayModeStateChanged(PlayModeStateChange state)
    {
        if (state == PlayModeStateChange.ExitingPlayMode)
            ClearAllBuses();
    }
#endif
}

public static class EventBus<T> where T : struct, IGameEvent
{
    private static Action<T> s_OnEvent;

    static EventBus() => EventBusRegistry.Register(Clear);

    public static void Subscribe(Action<T> listener) => s_OnEvent += listener;
    public static void Unsubscribe(Action<T> listener) => s_OnEvent -= listener;
    public static void Raise(T eventData) => s_OnEvent?.Invoke(eventData);
    public static void Clear() => s_OnEvent = null;
}

5.2. Vòng đời Subscribe/Unsubscribe: Lambda ẩn danh vs Named Method đối xứng

❌ ANTI-PATTERN: Dùng Lambda ẩn danh & ghép sai vòng đời 
public class BadHealthUI : MonoBehaviour
{
    private void Start()
    {
        // Lambda tạo ra một delegate instance mới -> KHÔNG THỂ Unsubscribe bằng -= được!
        EventBus<PlayerDamagedEvent>.Subscribe(e => UpdateBar(e.CurrentHp));
    }

    private void OnDestroy()
    {
        // VÔ TÁC DỤNG: Lambda mới khác hoàn toàn instance lambda đã tạo trong Start()!
        // BadHealthUI sẽ bị rò rỉ bộ nhớ vĩnh viễn trong static GC Root.
        EventBus<PlayerDamagedEvent>.Unsubscribe(e => UpdateBar(e.CurrentHp));
    }

    private void UpdateBar(int hp) { /* ... */ }
}
✅ BEST PRACTICE: Cặp đối xứng OnEnable / OnDisable với Named Method 
public class GoodHealthUI : MonoBehaviour
{
    // ĐỐI XỨNG 1:1 -> Bật lên là nghe, tắt đi (hoặc Destroy) là ngừng nghe ngay.
    // An toàn tuyệt đối với Object Pooling và Scene Unload.
    private void OnEnable() => EventBus<PlayerDamagedEvent>.Subscribe(OnPlayerDamaged);
    private void OnDisable() => EventBus<PlayerDamagedEvent>.Unsubscribe(OnPlayerDamaged);

    private void OnPlayerDamaged(PlayerDamagedEvent e) => UpdateBar(e.CurrentHp);
    private void UpdateBar(int hp) { /* ... */ }
}

5.3. Event Payload: class / Boxing gây GC Spike vs readonly struct Zero-GC

❌ ANTI-PATTERN: Payload là class hoặc truyền qua interface không generic 
// Lỗi: Class cấp phát trên Managed Heap mỗi lần 'new'
public class BadMoveEvent : IGameEvent
{
    public Vector3 Position;
    public BadMoveEvent(Vector3 pos) => Position = pos;
}

void Update()
{
    // Tạo rác GC mỗi frame -> gây giật khung hình (GC Spike)!
    EventBus<BadMoveEvent>.Raise(new BadMoveEvent(transform.position));
}
✅ BEST PRACTICE: readonly struct với Generic EventBus<T> (0 Heap Alloc, Immutable) 
// 1. readonly struct: Cấp phát trên Stack, immutable (subscriber không thể sửa dữ liệu giữa chừng).
public readonly struct PlayerMovedEvent : IGameEvent
{
    public readonly int EntityId;
    public readonly Vector3 Position;

    public PlayerMovedEvent(int entityId, Vector3 position)
    {
        EntityId = entityId;
        Position = position;
    }
}

void Update()
{
    // ZERO GC Allocation: Không cấp phát Heap, không Boxing.
    EventBus<PlayerMovedEvent>.Raise(new PlayerMovedEvent(gameObject.GetInstanceID(), transform.position));
}

5.4. Kiểm soát luồng: Ping-Pong Event Loop vs Fire-and-Forget cuối Pipeline

❌ ANTI-PATTERN: Bắn Event chéo nhau tạo vòng lặp vô hạn & phụ thuộc thứ tự 
// Hệ thống A bắn PlayerDiedEvent -> Hệ thống B nghe và bắn lại TryReviveEvent
// -> Hệ thống A nghe TryReviveEvent thất bại lại bắn PlayerDiedEvent
// => StackOverflowException làm crash Unity ngay lập tức!
// Ngoài ra, nếu SaveSystem và ScoreSystem cùng nghe PlayerDiedEvent, thứ tự chạy là NGẪU NHIÊN.
✅ BEST PRACTICE: Xử lý logic tuần tự xong xuôi rồi mới Raise thông báo 1 chiều 
public void ApplyDamage(int rawDamage)
{
    // 1. Logic cốt lõi có thứ tự chặt chẽ thực hiện TUẦN TỰ bằng direct call
    int finalDamage = _armor.Mitigate(rawDamage);
    _hp -= finalDamage;

    if (_hp <= 0 && !_reviveModule.TryConsumeRevive(ref _hp))
    {
        // 2. Chỉ khi state ĐÃ CHỐT XONG hoàn toàn mới phát EventBus 1 chiều
        // cho UI, Audio, Analytics tự phản ứng độc lập.
        EventBus<PlayerDiedEvent>.Raise(new PlayerDiedEvent(_score.CurrentScore));
    }
}
PHẦN 6

Senior Checklist Trước Khi Merge Pull Request

Kiểm tra nhanh 6 tiêu chuẩn vàng dưới đây trước khi đưa code sử dụng EventBus<T> vào nhánh chính:

  • ✅
    Đối xứng Subscribe / Unsubscribe: Mọi lệnh Subscribe trong OnEnable đều có cặp Unsubscribe tương ứng trong OnDisable (hoặc Awake / OnDestroy), tuyệt đối không dùng lambda ẩn danh.
  • ✅
    Payload là readonly struct: Sự kiện kế thừa IGameEvent được khai báo là readonly struct gọn nhẹ để đạt Zero-GC Allocation và tránh subscriber sửa dữ liệu của nhau.
  • ✅
    An toàn Domain Reload: Đã tích hợp EventBusRegistry.ClearAllBuses() với [RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.SubsystemRegistration)] và không xóa nhầm danh sách s_ClearActions.
  • ✅
    Không phụ thuộc Execution Order: Không có hai subscriber nào cùng lắng nghe một event mà logic của subscriber này đòi hỏi phải chạy sau subscriber kia.
  • ✅
    Không tạo Event Loop: Đã kiểm tra luồng sự kiện đảm bảo không có chuỗi gọi vòng tròn (Event A → Event B → Event A).
  • ✅
    Unit Test sạch sẽ: Mọi bài Unit Test có đụng tới EventBus<T> đều gọi EventBusRegistry.ClearAllBuses() trong [TearDown].
